CASO DE ESTUDIO DESTACADO · UX/UI & BACKEND

SmartTicket: De la experiencia del usuario a la arquitectura de datos

Rol: Diseñador UX/UI & Desarrollador Backend | Año: 2026 | Stack: Figma, Python, FastAPI, SQLAlchemy, Uvicorn

Ver Prototipo en Figma ↗ Ver Código en GitHub ↗ Explorar Swagger API ↗

El Problema (Fricción en la compra de tickets y validación de eventos)

Comprar entradas para eventos de alta demanda suele ser una experiencia frustrante para el usuario y crítica para el servidor. Desde el lado de la experiencia (UX), las plataformas tradicionales sufren de costos ocultos hasta el último paso, formularios interminables y mensajes de error ambiguos cuando se agota el cupo. Desde el lado técnico, el diseño de interfaz suele realizarse de forma aislada a la lógica del backend, generando inconsistencias cuando dos usuarios intentan reservar la misma ubicación en simultáneo.

El Proceso UX (Definición de usuario, arquitectura, wireframes y decisiones de interfaz)

El proceso comenzó definiendo dos perfiles clave: el comprador que busca asegurar su entrada en menos de dos minutos desde el celular, y el organizador que necesita controlar el aforo en tiempo real. A través de un mapa de arquitectura de información, eliminé los pasos innecesarios y estructuré un flujo de conversión directo en 3 etapas: Selección visual de sector → Resumen transparente de costos → Confirmación instantánea. En la etapa de wireframing en Figma, prioricé el diseño de casos borde (edge cases): pantallas de carga (skeletons), estados vacíos y alertas preventivas claras antes de enviar el formulario.

La Solución UI y Técnica (Jerarquía visual clara, estados de carga/error y respaldo con API rápida en FastAPI)

Diseñé un sistema de componentes con alto contraste (WCAG 2.2 AA) donde la disponibilidad de cada evento se comunica mediante badges semánticos inmediatos ("Disponible", "Últimas ubicaciones", "Agotado"). Para respaldar esta interfaz sin demoras, construí una API RESTful asíncrona utilizando Python y FastAPI sobre un servidor Uvicorn. Modelé la base de datos relacional con SQLAlchemy asegurando la integridad de cada orden de compra, y alineé cada componente de Figma con los esquemas de respuesta JSON documentados en Swagger. Así, cada estado de error o éxito de la API (200, 400, 404, 409) tiene su correlato exacto y humano en la interfaz.

Resultados y Aprendizajes (Métricas de usabilidad y aprendizajes del trabajo)

  • Impacto en Usabilidad: Reducción del flujo de reserva a solo 3 pantallas principales, disminuyendo la carga cognitiva y eliminando puntos de abandono por falta de información de precios.
  • Eficiencia en Desarrollo: El diseño de componentes basado en contratos de API redujo a cero el retrabajo entre el prototipo de Figma y la estructura de endpoints en FastAPI.
  • Aprendizaje Clave: Pensar el modelo de datos en SQLAlchemy al mismo tiempo que los flujos de usuario en Figma permite anticipar errores de concurrencia y transformarlos en microinteracciones claras que guían al usuario en lugar de frustrarlo.
